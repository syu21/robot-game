# 実験室UGC投稿・展示・採用システム 実装仕様書

最終更新日: 2026-04-11

対象: ロボらぼ

目的: 実験室におけるユーザー投稿ロボの展示文化を育てつつ、将来的に本編へ安全に採用できる仕組みを整備する。

前提: 実験室は、本編の強さ、コイン、層進行、出撃、進化、強化とは分離した `観戦 / 展示 / 語り` の場である。

運営思想との接続: ロボらぼは現在チュートリアルフェーズにあり、優先すべきは `周回快感`、`自然競争`、`語りの発生` である。PvP は最後に置く。

## 0. 現行実験室との互換

この仕様は、現行の実験室仕様を置き換えない。

既存の以下は維持する。

- `/lab` の実験室トップ
- `/lab/race` 以降のエネミーレース
- `/lab/race/prizes` などの lab casino / 観戦導線
- `/lab/upload`
- `/lab/showcase`
- `/admin/lab`
- 既存 `audit.lab.*` 互換
- 本編の `/showcase` にある実戦機展示

本仕様で新たに定義するのは、実験室投稿ロボを `創作文化` として育て、必要に応じて本編採用候補の原案プールへ接続するための上位ルールである。

## 1. この機能の役割

本機能は、ユーザーが作成したロボ画像を実験室へ投稿し、承認後に展示、話題化し、さらに運営判断で本編世界へ逆流させるための仕組みである。

本編に既に存在する展示は、`自分で育てた / 編成した / 思想が乗った実戦機の展示` として維持する。

一方、実験室UGC展示は、`ユーザーが投稿した創作ロボ / 試作ロボ / 研究機体の展示` として分離する。

この分離により、次の二層構造を成立させる。

- 本編展示 = 実戦文化
- 実験室展示 = 創作文化

## 2. 一文で言うと

実験室は、投稿ロボを並べて終わる場所ではなく、ユーザーの創作が将来的にロボらぼ本編へ正式採用されうる `研究開発区画` として運営する。

## 3. 目的

### 3.1 主目的

- ロボのコンテンツ不足を `創作文化` で補う
- 少人数でも `人がいる / 世界が育っている` 感を強める
- ロボを誇る軸を、実戦だけでなく創作にも広げる
- 投稿ロボを将来的な本編実装候補プールにする

### 3.2 副目的

- 世界ログ、通信、実験室話題と接続して話題を生む
- ユーザーが `自分も世界作りに参加している` と感じられる状態を作る
- 敵機、イベント機、外装、ドロップ候補の原案プールを蓄積する

## 4. 絶対に守る前提

### 4.1 本編戦力とは分離する

投稿行為それ自体で、本編戦力、進行、勝率に直接影響しない。

これは実験室全体の方針と一致させる。

### 4.2 投稿物をそのまま販売・実装しない

ユーザー投稿ロボは、あくまで `原案` として扱う。

本編に出す場合は、必ず次の順を踏む。

1. 投稿原案
2. 運営審査
3. 運営再構成
4. 正式採用

### 4.3 承認制を必須とする

公開前に運営が内容を確認する。

これにより、世界観、品質、権利、表示整合、採用候補の安全性を守る。

### 4.4 採用を保証しない

投稿は展示の機会を与えるものであり、本編採用、商品化、敵化、ドロップ化を保証するものではない。

### 4.5 投稿時に利用条件へ同意させる

投稿時に、利用規約と同意文を明確に通す。

特に `展示利用`、`本編採用候補としての検討`、`採用や報酬の非保証`、`運営再構成版としての採用可能性` は必ず明記する。

## 6. 投稿対象の定義

### 6.1 投稿対象

ユーザーが作成したロボ画像投稿を対象とする。

初期段階では、完成ロボ1枚画像投稿を正規とする。

将来的に、以下の4パーツ分割投稿へ拡張可能とする。

- 頭 + 胴体
- 右腕
- 左腕
- 脚

### 6.2 なぜ最初は1枚投稿か

4パーツ投稿は魅力的だが、初期から必須にすると投稿ハードル、承認コスト、UI負荷が上がり、投稿数が増えにくくなる。

まずは文化の形成を優先し、v1 では1枚投稿とする。4パーツ制は v2 以降で拡張する。

## 7. 投稿UI文言方針

世界観を壊さないため、実験室では `投稿` より以下のような文言を優先する。

- 試作機登録
- 研究機体提出
- 試験展示申請
- 実験室アップロード
- 研究所審査待ち

reject も `不採用` より以下のような表現へ寄せてもよい。

- 再提出待ち
- 展示保留
- 条件未達
- 研究所差し戻し

ただし、分かりやすさを優先し、内部状態名は `pending / approved / rejected / disabled` で保持する。

## 9. 利用条件・権利処理

### 9.1 投稿時同意の基本方針

投稿前に、ユーザーに以下を明確に同意させる。

#### 投稿者保証

- 投稿者は、投稿画像について自分が権利を持つ、または適法に利用可能な素材のみを用いていることを保証する
- 第三者の権利を侵害する画像を投稿しないことを保証する

#### 展示利用許諾

- 運営は、投稿画像を実験室およびロボらぼ関連画面で展示、縮小、トリミング、紹介、ランキング表示、話題表示に利用できる

#### 軽微修正の許諾

- 運営は、表示上必要な範囲で、サイズ変更、トリミング、背景調整、軽微な演出調整を行える

#### 本編採用候補としての取り扱い

- 投稿画像は、本編実装、敵化、イベント化、外装化、ドロップ機体化等の候補原案として検討される場合がある
- ただし、投稿画像そのものをそのまま使うのではなく、運営が再構成、再デザイン、再生成、再描画した上で採用する場合がある

#### 採用の非保証

- 投稿により本編採用、商品化、特典付与を保証しない

#### 対価の非保証

- 投稿に対する報酬、対価、金銭、無償有償を問わず採用時の補償を保証しない
- 必要に応じて、クレジット表記や称号等の非金銭的対応を行う場合があるが、これは運営判断とする

#### 表示名利用

- 運営は、投稿者名または表示用クレジット名を、展示ページおよび採用時の紹介文に掲載できる

#### 削除と存続

- 投稿が展示停止や非公開となっても、監査、履歴、権利確認のため最小限の記録を保持できる

### 9.2 重要な実務方針

揉めないためには、`ユーザー投稿をそのまま商品や敵にする` 構造を避けることが重要である。

必ず `運営による再構成版` を正式実装物とする。

### 9.3 利用条件UI

投稿画面に長文をそのまま載せず、以下の2段構成にする。

短文要約:

- 投稿画像は実験室展示と、将来の本編採用候補として利用される場合があります
- 採用時は運営側で再構成されることがあります
- 採用や報酬は保証されません

詳細:

- 詳細利用条件へのリンクを設置する
- 同意チェックを必須にする

### 9.4 記録必須項目

投稿時点で以下を保存する。

- 同意バージョン
- 同意日時
- 投稿時利用条件本文のスナップショット
- AI生成申告欄
- 任意の制作メモ

## 12. 投稿フロー

### 12.1 ユーザーフロー

1. ユーザーが `/lab/upload` を開く
2. タイトル、コメント、PNG、同意チェックを入力する
3. 投稿する
4. `pending` で保存する
5. 個人用マイ投稿一覧では `審査待ち` と表示する
6. 承認後、`/lab/showcase` に公開する
7. 公開後、いいね、話題化、注目入りが起こる

### 12.2 管理者フロー

1. `/admin/lab/submissions` で `pending` 一覧を確認する
2. 画像、タイトル、コメント、権利情報を確認する
3. `approve / reject / disable` を行う
4. 承認時に必要ならタグ、チャート値、feature、adoption_candidate を付与する
5. `approved` のみ公開する

## 14. レーダーチャート仕様

### 14.1 目的

本編性能とは独立した `機体らしさ`、`研究資料感` を演出するために使う。

### 14.2 軸

本編と同じ6軸表示に揃える。

- 耐久
- 攻撃
- 防御
- 素早さ
- 命中
- 会心

### 14.3 値の意味

これらは `実験室用の印象値 / 演出値` とする。本編戦闘性能とは一致しない。

### 14.4 初期付与方法

初期は自動推定ではなく、承認時に管理者が 1〜100 の範囲で半手動設定する。

理由:

- 変な自動判定を避ける
- 運営が空気を作れる
- 表示の納得感を保てる

### 14.5 UI注意

レーダーチャート付近に短く `実験室用の参考スペックです` と補足を置く。

## 15. 本編採用ポリシー

### 15.1 基本

投稿ロボは、そのまま本編へ実装しない。

必ず運営側が正式採用版へ変換する。

### 15.2 採用先種別

投稿ロボ原案は以下のいずれかに採用されうる。

- 敵機
- イベント敵
- ドロップ機体
- イベント報酬機
- DECOR / 外装
- ショップ向け外装
- 実験室専用キャラ
- その他演出素材

### 15.3 優先順位

導入しやすさと揉めにくさの観点で優先順位は以下。

1. 敵機
2. イベント敵 / 実験室イベント機
3. ドロップ機体
4. DECOR / 外装
5. ショップ追加

### 15.4 なぜ敵機優先か

- 運営が性能を自由に設計できる
- 世界観に載せやすい
- 投稿者との利害が比較的ぶつかりにくい
- 既存ユーザー全員が触れられる

### 15.5 商品化は慎重に

ショップや課金導線に載せる場合、特に権利と感情の摩擦が起きやすい。

課金要素にする場合は、以下を守る。

- そのままの画像利用を避ける
- 運営再構成版にする
- クレジットの扱いを事前設計する
- 必要なら個別確認フローを将来追加する

## 16. 採用運用の内部ルール

### 16.1 採用候補とは何か

`is_adoption_candidate=1` は、`運営が面白いと判断した候補` であり、実装決定ではない。

### 16.2 実装時の原則

- 投稿画像そのものを本編アセットとして使わない
- 運営が再構成した正式版アセットを作る
- 性能、属性、所属、名前、レアリティは運営が決める
- 原案者へのクレジット表記は可能な範囲で行う

### 16.3 クレジット

表示するなら以下のように寄せる。

- 原案提供: ○○
- 実験室出身機体
- 第一期採用機
- 研究員設計原案

### 16.4 クレジット必須にしすぎない

匿名希望や表示名変更もあり得るため、内部保存はしても、公開時の表示名は別管理にする。

## 17. モデレーション仕様

### 17.1 approve

- 公開可
- タグ付け可
- レーダーチャート付与可
- feature 可
- adoption candidate 可

### 17.2 reject

- 非公開
- 理由をテンプレで残す
- ユーザー側に分かりやすく見せる

### 17.3 disable

一度公開後に停止する。

権利問題、通報累積、世界観逸脱、運営判断などで使用する。

### 17.4 reject理由テンプレ

- 透過条件を満たしていません
- サイズ条件を満たしていません
- ロボらぼの掲載方針と合いませんでした
- 権利面の確認ができませんでした
- 画像内容に問題がありました
- 再提出をお願いします

## 19. 世界ログ・話題化

実験室は閉じた場所にしない。

世界ログや実験室トップの話題と接続する。既存でも実験室トップには `今週の実験室話題` を出す前提がある。

### 19.1 話題化イベント例

- 初投稿承認
- 今週の注目機
- いいね急上昇
- 採用候補入り
- 正式採用決定
- 実装完了

### 19.2 出し方

本編の世界ログにノイズとして混ぜすぎない。

まずは `/lab` トップの `今週の実験室話題` に集約し、必要に応じて世界ログに一部だけ流す。

## 23. 文言草案

投稿画面の同意欄に載せる短文案:

```text
投稿前にご確認ください

投稿画像は、実験室での展示や紹介に利用されます。
運営は表示のために縮小・トリミングなどの軽微な調整を行う場合があります。
投稿画像は将来的に本編実装の原案候補として検討される場合がありますが、採用や報酬を保証するものではありません。
本編に採用される場合、運営側で再構成・再制作した正式版として実装されることがあります。
他者の権利を侵害する画像は投稿できません。
```

チェック文言案:

```text
上記および詳細利用条件に同意して投稿する
```

## 24. 運営ルール

### 24.1 採用判断は運営専権

採用は人気投票ではなく、最終判断は運営が行う。

### 24.2 似た投稿が来ても先着優先にしない

採用は先着保証にしない。

世界観、完成度、実装相性を優先する。

### 24.3 本編実装時に性能連動しない

実験室のレーダーチャートや見た目印象は、本編性能と一致しなくてもよい。

### 24.4 問い合わせ窓口を用意

投稿削除依頼、権利申告、異議申立てに備え、問い合わせ導線を付ける。

## 25. 最後の設計思想

この機能の成功条件は、投稿数そのものではない。

成功条件は、次の4つである。

- 投稿者が `出してよかった` と思う
- 見る側が `見に行く理由がある` と思う
- 運営が `本編へ逆流させたい` と思う
- 世界に `このゲームは育っている` と感じさせる

## 26. 最終まとめ

今回の正しい方針は以下である。

- 本編展示はそのまま維持する
- 実験室展示は投稿ロボ専用文化圏にする
- 投稿は承認制にする
- 投稿画像は展示用であり、同時に本編採用候補の原案として扱う
- ただし、そのまま本編に出さず、運営再構成版として正式採用する
- 投稿時に利用条件と権利同意を必須化する
- 監査、同意履歴、採用管理を残す
- 採用は敵機から始めるのが最も安全である
- 課金要素化は一番慎重に扱う
