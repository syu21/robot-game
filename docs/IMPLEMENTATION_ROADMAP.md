# ロボらぼ 実装優先ロードマップ

最終更新日: 2026-08-09

この文書は、ロボらぼの実装優先順位を忘れないための正本メモです。
`docs/GAME_DIRECTION.md` に書かれた運営思想を、具体的な実装順に落としたものとして扱います。

新機能、改善案、UI調整、運用施策を考えるときは、
「今どの Phase を進めているか」
「その実装が Phase の目的に合っているか」
を必ず確認してください。

## 1. この文書の前提

ロボらぼは現在 `チュートリアルフェーズ` にある。

今の探索・強化・進化・ボス・DECOR取得は、
完成したゲーム本編ではなく `基礎体験の提供段階` である。

現時点の診断を短く言うと、
`ゲームはできているが、世界の熱量がまだ足りない` 段階にある。

第3層までの導線とコアループは成立しつつある一方で、
プレイヤー人口が少ないため `世界が動いている感じ` が弱く、
無人感が体験価値を削っている。

当面の優先は次の通り:

- β版として `公開入口(/ -> /register) -> 登録 -> ホーム -> 初戦闘 -> 戦利品 -> 再出撃/育成` の入口体験を磨く
- 周回快感を上げる
- 型 / 思想の自然発生を作る
- 世界ログ / ランキング / 展示 / 陣営戦で間接競争を育てる
- プレイヤー同士の研究・語り・記録文化を作る
- 実験室UGC投稿を `創作文化` として育て、将来的な本編採用候補の原案プールにする
- 少人数でも `人がいる / 世界が動いている` 感じを成立させる

`PvP は入口ではなくゴール` とする。
早期に PvP を主役にしない。

## 2. 判断基準

今後の実装は、必ず次の3条件で判断する。

### 2-1. 周回が気持ちよくなるか

確認観点:

- 毎周回の入力ストレスが減るか
- 前進感が増えるか
- 勝ち体験や報酬感が気持ちよくなるか
- もう1周したくなるか

### 2-2. 競争が自然発生するか

確認観点:

- 他人との比較軸が自然に生まれるか
- ランキング、記録、展示、陣営戦に繋がるか
- プレイヤーごとの差が可視化されるか
- 間接競争を強めるか

### 2-3. プレイヤーの語りが生まれるか

確認観点:

- スクショを貼りたくなるか
- X / Discord で話題にしやすいか
- 自分の育成思想を語れるか
- 他人のロボを見て真似や研究が生まれるか

## 3. 固定制約

今後の実装では、次を壊さないこと。

- 第1〜3層は8ターン判定を維持し、第4層以降は現行コードどおりターン上限なしでHP決着を優先する
- `audit.*` 互換を維持する
- `turn_logs` 互換を維持する
- `SYSTEM` 投稿の既存方針を壊さない
- 実装変更時は `docs` 更新と `tests` 更新を必須とする
- 公開は `一気に見せる` のではなく、`管理者確認 -> 段階公開` を優先する

## 4. 実装優先順

### β版入口改善

短期的な最優先は、新機能追加ではなく `入口〜初戦闘` を完成させること。
現行の公開入口はまだ `/register` 中心で、`/` の専用LPは準備段階とみなす。

優先順:

1. 公開入口（現状 `/register`、将来的に `/`）で `何のゲームか / 世界が動いているか / 今始めていいか` を3秒で伝える
2. 登録を軽くし、Google登録を含めて登録直後にホームからそのまま第1層へ出撃できるようにする
3. ホームの `初任務` と `Next Action` を、最初の1勝へ直結する文言に寄せる
4. 戦利品結果面で `もう一度出撃 / 入手したパーツを見る / ホームへ戻る` を短く出し、押しやすくする
5. 支援導線は `支援2本 + 利便性1本` の3商品に絞り、強さ販売に見えないようにする

定点観測修正:

- 登録直後から初回出撃前まではホーム主CTAを `初任務` / `第1層へ出撃` に統一する
- 初回勝利後から3出撃未満までは同じ主CTA位置で第1層再出撃を促す
- `EXPLORE_START` は `entry_source`, `home_session_id`, `seconds_from_home_view`, `is_first_explore`, `explore_count_before` を記録する
- 戦闘結果直表示でも `BATTLE_RESULT_VIEW` を必ず記録し、結果表示率とretry率が分断されないようにする
- DAU は実ユーザー操作イベントだけで集計し、管理者、BAN、集計除外、攻撃風登録名を除外する
- ボス遭遇は `boss_source=normal/pity/guaranteed/guaranteed_retry/fixed/admin_test/unknown` で分類する

## Phase 3.5: 世界創造フェーズ

目的:

- 無人感を消し、世界が常に動いて見える状態を作る
- 少人数でも「遊ばれている世界」に見える基盤を作る
- 新規流入時に、静かなゲームではなく `動いている世界` として返す

現在地メモ:

- 2026-03-29 時点では、第3層までの体験は成立しつつある
- 問題は `ゲーム性不足` より `世界の活動量不足` に寄っている
- 当面は新モード追加より `視覚 / ログ / 用事` を優先する
- 今やるべきことは `ロボを動かす / 人がいる感を作る / 今日の用事を作る`
- 2026-04-02 `通信 / 世界戦況 / 記録庫 / ランキング` で recent activity と presence 表示を先行反映した
- 2026-04-06 `今週のチャンプ機体` を追加し、`王者 / 挑戦 / 撃破報告` を world log とホームで見える文化として先行実装した。一般公開前は管理者だけ先に確認できるよう release gate を追加
- 2026-04-06 `services/balance_simulator.py` と `tools/run_balance_simulation.py` を追加し、7型×複数テンプレの総当たりで勝率マトリクス / 危険対面 / 万能候補 / 死に型候補を開発用に確認できるようにした

実装原則:

- 重い GIF ではなく、CSS アニメーションや 2〜4 コマの軽量スプライトで見せる
- `人がいる感` は、実ユーザー数の偽装ではなく `実活動ログ + 世界設定に沿った存在演出` で作る
- BOT や補助アカウントを使う場合は、実プレイヤーと誤認させるためではなく、世界内の `研究員 / 訓練機 / 展示機` として扱う
- リアルタイム PvP やマッチングは、この段階では主役にしない
- 新規プレイヤーが 10 秒で「何かが起きている」と理解できる画面を優先する

### 16. ロボの軽量アニメーション

狙い:

- 画面の静止感を消す
- 小型機体アイコンの存在感を増やし、世界が生きている印象を作る
- 滞在時間と再訪率を上げる

完成条件の例:

- `ホーム / 今週のMVP / ランキング / 世界ログ` の小型機体アイコンが軽く動く
- 常時は `ふわふわ / 呼吸 / まばたき` などの軽い動きに留める
- `出撃中 / 待機中 / 放置` で速度差をつけられる余地を持つ
- 重い画像演出や大量通信なしで描画できる

### 17. 活動ログと在線感の強化

狙い:

- 「人がいる感」を強制的に可視化する
- 世界ログと会議室を、単なる投稿置き場ではなく `世界の呼吸` に変える

完成条件の例:

- `ログイン / 出撃開始 / ボス撃破 / 進化成功` が世界ログに自然に流れる
- 会議室や通信で `最近5分で動いた人数` のような軽い存在表示ができる
- `今○人が活動中` のような表示は、実計測ベースで作る
- 活動量が少ない時間帯でも、世界設定に沿った補助ログで空白感を減らせる

### 18. 今日の用事を作る

狙い:

- 再訪理由を作る
- 「遊ぶ理由がない」を防ぎ、少人数でも日次の習慣を作る

完成条件の例:

- `今日の出撃 / 今日のボス / 今日の挑戦` が短く見える
- 1 回のログインで達成できる軽い用事から始める
- 報酬は強さを壊さず、通貨 / DECOR / 記録系で回す

### 19. 比べる文化の下準備

狙い:

- PvP を入れる前に、比べる文化だけを先に作る
- 展示・記録・挑戦の流れを強くする

完成条件の例:

- `今週の挑戦ロボ` のような全員共通の相手がある
- `今週のチャンプ機体` を全員共通の相手として置き、勝敗と撃破報告を非同期に積み上げられる
- 展示ロボとの模擬戦や AI 戦の入口を検討できる
- `復讐` のような感情導線は、非同期形式で扱う
- リアルタイム PvP なしでも「比べたい」が生まれる
- その前提として、`balance_simulator` で型相性の極端な偏りや万能型候補を先に検知できる

### 20. 流入向け体験投稿の型を作る

狙い:

- 集客を `更新報告` ではなく `体験投稿` に寄せる
- クリックしたくなる入口を増やす

完成条件の例:

- `10秒でロボを作れる`
- `このロボどう育てる？`
- `命中999が出た`

のような短い投稿テーマが運営内でテンプレ化されている

次段階メモ:

- 収益化は `強さ販売` ではなく `時間 / 見栄 / 参加` を軸に設計する
- `異常ロボ` は強い案だが、世界が動き始めてから投入する
- 非同期 PvP は有力候補だが、リアルタイム PvP より先に `展示 / AI / 今週の挑戦` を固める
- 廃品市場はまず `admin_only` で経済検証し、探索3回前後でN購入に触れるか、レースが副収入に留まるかを見てから `public` へ切り替える

- 目的: BATTLE CODEをSINGLE/DUAL対応にし、2つの戦術条件のうち先に成立した命令を1度だけ実行する。
- 条件: 既存conditionを維持し、敵trait条件 `enemy_heavy/fast/berserk/unstable` を追加する。
- 保存: 既存3枠を維持。v1 rowはLOGIC Aのみとして読む。LOGIC Bは任意。
- 接続: 戦術セット保存/適用でactive BATTLE CODEを一括復元する。削除済みCODEは適用中止。
- 監査: 既存BATTLE CODE audit payloadへ `code_version`, `logic_entries`, `triggered_logic`, `fallback_success` を追加する。

## Phase 4.1: パーツ機構特性 v1

- 目的: パーツに敵特性対策の判断軸を追加し、同じ総合性能でも出撃先や相手で構成を考え直す理由を作る。
- データ: `robot_parts.mechanism_trait_key` を正本にする。`part_instances` へコピーせず、個体差・強化・進化引き継ぎを壊さない。
- 発動: Nは非発動、R以上で発動。効果量は全レアリティ共通。
- 対象: HEAD / RIGHT_ARM / LEFT_ARM / LEGSに最大1つずつ、合計最大4つ。DECORは対象外。
- 戦闘: 既存敵特性 `heavy / fast / berserk / unstable` に小さな補正を与える。HPだけを伸ばす調整やシリーズボーナス追加はしない。
- UI: `/parts`、強化・進化、`/build`、戦術セット、通常戦闘結果、異常個体結果へ表示する。
- 管理: `/admin/metrics` でR+装備、発動戦闘、特性別勝率、第6層勝率、異常個体CLEAR率を確認する。
- 監査: 既存 `audit.explore.end` と `audit.anomaly.attempt` に集約payloadを追加する。

## Phase 4.3: 全体パフォーマンス改善 v1

- 目的: ゲーム挙動・画面情報・URL・auditを変えずに、ページ表示と通常操作の体感待ち時間を減らす。
- 実装範囲: request内キャッシュ、ログ出力抑制、静的ファイル存在確認の重複削減、既存ロボ画像の不要再合成抑制。
- 計測: `X-Robolabo-Elapsed-Ms` と `PERF_DIAGNOSTICS=1` のSQL/テンプレート計測を継続利用する。ホームsectionログは通常停止し、必要時だけ `HOME_SECTION_LOG_ENABLED=1` で出す。
- 非目標: 戦闘ロジック、乱数順、ドロップ率、CT、報酬、決済、URL、画面情報の削減。

## Phase 4.4: 今日の研究指令 v2

- 目的: 全員共通の日次指令を、ユーザー進行度に合う「今日試す研究」へ拡張する。
- 生成: `sortie / training / tendency` の3件を維持し、未解放area、強化不能、進化未解放を候補から外す。

- UI: ホームは3行表示のまま、1件だけ `おすすめ研究` として軽く強調する。
- 計測: 表示→進行、進行→完了、完了→全完了、翌日再訪を管理メトリクスへ追加する。

## Phase 4.5: 戦利品パーツ即時評価・更新候補 v1

- 目的: 通常出撃で拾ったパーツを、その場で現在装備と比べたくなる導線にする。
- 対象: 通常出撃で入手した HEAD / RIGHT_ARM / LEFT_ARM / LEGS の `part_instance`。DECOR、進化コア、自動装備は対象外。
- UI: battle result のドロップ行に `更新候補` または個性ラベル、総合差分、最大3ステ差分、`このパーツを見比べる` を小さく表示する。
- `/parts`: `focus_part_id` は本人所有の inventory/equipped だけ受け付け、対象に `今回入手` を付けて比較欄へ自動表示する。
- 編成接続: focusパーツには既存 `/build` の部位選択クエリで `このパーツで編成を試す` を出す。交換はユーザーが手動で確定する。
- 監査: 新規イベントは追加せず、既存 `audit.drop` payload に `dropped_part_instance_id / compared_equipped_part_instance_id / total_delta / standout_stat / recommendation_key` を追加する。
- 非目標: 自動装備、絶対的な強弱判定、強力報酬、新DBテーブル、周回を止めるモーダル。
